- F28 — B10.5 BUG 2: cleaner dispatch was not property-scoped. Both checkout paths — manual `checkout` and `settleAutoCheckout` — ran the identical unscoped query `airtableGet('WS_Cleaners', '{Active} = TRUE()')`, so every active cleaner in the base was notified on every checkout regardless of property. Invisible with one property live; a guaranteed cross-property leak the moment a second exists. (The gate report expected the auto path to scope via the Booking→Room→Property walk — it does not; that walk only feeds `propertyName` into the guest's message copy and never reached the cleaner query, so both paths leaked identically and there was no dead scoping to strip.) Fix (decision (c)): persist the property on the booking — check-in writes `WS_Property: [ctx.property.id]` into the arrival handler's existing `bookingUpdate` (no new call; `ctx.property` is already resolved from the inbound `phone_number_id`) — and scope both checkout paths off that record via one shared helper pair, `bookingPropertyId` / `activeCleanersForProperty`, so there is a single scoping mechanism rather than two. Scoping is by property **record id**, never by name: Airtable's `filterByFormula` matches linked-record fields on their primary display value, so the id-safe route is fetching active cleaners and filtering the link array in code (same reasoning as `airtableGetBookingsByGuestId`). Resolution order is booking's `WS_Property` → `ctx.property.id` / room-walk `propId` → **nobody**: pre-fix bookings carry no `WS_Property` and stay correctly scoped via the fallback, and an unresolvable property fails closed, since the bug being fixed is notifying everyone. Live schema confirmed via meta API: `WS_Bookings.WS_Property` (link→WS_Properties, single) and `WS_Cleaners.Assigned Property` (link→WS_Properties, multi) — the latter **does** exist live despite being absent from trunk code and from the stale `schema.json`; both are now recorded there. Covered both paths with two properties and exclusion assertions (three cleaners, all Active, so only property scoping can exclude anyone): `fixtures/61_manual_checkout_property_scoped.json` for manual — its room is deliberately left without a Property link so a room-walk implementation would fail it — and `test/autocheckout.test.js` for the cron, which the fixture harness can't replay because it is time-driven, plus a fail-closed case. Red/green verified: unfixed auto-checkout sends 4 messages (property B's cleaner and an unassigned cleaner included), fixed sends 2. Seeds in `fixtures/10`, `fixtures/58` and the existing B12 test needed `Assigned Property` added — under scoping those cleaners were correctly excluded. **Supersession (CEO-decided, not deferred to merge time): `feature/b11-cleaner-property-link` (`11dbbc4`) is superseded IN FULL — its entire diff was manual-path scoping, which this fix replaces with a better source (the booking record, not the cleaner) and extends to the auto path. `feature/b11-5-cleaner-guest-precedence` was stacked on it; it is rebased onto this fix with the scoping hunk dropped, keeping only `guestStateExpectsInput` + fixtures 62/63, which are independent of scoping. B11's `fixtures/43` is superseded by `fixtures/61` (61 also leaves its room without a Property link, so it catches a room-walk regression that 43 does not). One scoping source survives regardless of merge order — the point of decision (c). The arrival write is conflict-free; no branch touches it.**

- F27 — B10.5 BUG 1: `airtableGet` pagination. The helper did a single `fetch` and returned `data.records`, but Airtable's list API caps a response at 100 records and signals more via an `offset` token — so past 100 rows it silently truncated (no error). `logEnquiry`'s dedup guard then read a short list, missed the booking's own row, and every completed overnight booking double-logged (Booked reached at both `collectDetails` and `recordEta`), inflating revenue and turned-away counts. Fix: loop on `offset`, accumulating every page until the response has none. Verified past the boundary — the mock harness now mirrors Airtable's 100-record paging, and `test/enquiry.test.js` seeds 120+ realistic `WS_Enquiries` rows then completes a booking and asserts exactly one Booked row; that test passes with the loop and fails without it, while every sub-100 test stays green (the bug is invisible under 100). The fix corrects **every** `airtableGet` call site at once; the PR's audit lists each as bounded or unbounded-in-size, flagging `WS_Enquiries` `''` (logEnquiry/sweep) and the B17 all-non-cancelled-bookings query as the ones that fetch large/growing sets and should gain server-side filters (follow-up, not this commit). **Note: live-base verification against 100+ real rows is a CEO device-test — `WS_Enquiries` does not exist in `appgtVqX1dK88lpRT` yet (Shawn creates it), so it currently holds zero rows.**
