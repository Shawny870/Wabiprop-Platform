- F33 — B7 (WALKIN), **part 1 of 2: command grammar only.** `parseWalkinCommand` + `test/walkin.parser.test.js` (19 tests). The schema-dependent half — the `WS_Roles` authorisation lookup, room resolution, the availability re-check and the booking write — is **deliberately not in this commit**: neither Airtable precondition was live when it was written (`WS_Roles` ABSENT from the base; `WS_Bookings.Source` still `WhatsApp | Walk-in Cash | Phone Call` with no `Walk-in` option), and hard rule 22 forbids writing a field name that cannot be read from the live schema. Verified live this session, not assumed. **The grammar is strict on two points and both are live-data hazards, not style.** Villa Liza has 12 rooms — `Room 01`…`Room 12`, `Room Number` 1–12 — so `WALKIN 12 2` is two bare numbers with two equally valid readings and no safe default; booking the wrong one puts a stranger in an occupied room. The **ROOM keyword** is therefore mandatory (it is the only thing separating the two positions) and so is the **hour unit** (`2hrs`, never bare `2`), which is what makes `WALKIN ROOM 12 2HRS` unambiguous even though both tokens are numbers and both are valid room numbers. **Critically, `roomMatchesText` is NOT reused here and is left untouched:** it tests `\b<number>\b` anywhere in the message, so run over `WALKIN ROOM 12 2HRS` it matches Room 02 on the DURATION digit — staff say twelve, the system books two. That helper is correct where it is used (a cleaner naming a room in free text, only ever after the sender is confirmed a registered cleaner) and wrong here; this parser exists so it does not have to change. **Duration is locked to 1/2/3 hours** (CEO, 6 Aug), reusing `HOURLY_DURATIONS` rather than a second literal so the command and the rate card cannot drift apart. 4+ is refused with the requested value rather than repriced: the overnight rate is occupancy-keyed (F19) and a walk-in has no guest to ask, so there is no price for a 4-hour stay, and inventing one would be the exact F19 failure — a price chosen by something other than a decision. **Three return shapes, and the `null` / `{ok:false}` split is the no-leak boundary:** `null` means "not a WALKIN attempt", the guard declines, and the message falls through to the ordinary guest flow so an outsider sees precisely the greeting any stranger sees; `{ok:false}` means "malformed WALKIN", and only an authorised sender ever reaches the handler that answers it. Collapsing the two would make the reply to a stranger depend on whether they typed a real command — the leak the CEO ruled out, and the reason there is no separate "generic reply" path to build. The keyword must LEAD the message, so a guest sentence containing "walk in" stays `null` and that guest's reply is unchanged. **One test was corrected rather than the parser:** `walkin room two 2hrs` parses as room token `two`. `Room A` exists in the fixtures so alphabetic tokens must be allowed, which makes a word token indistinguishable in shape from a real room name — the parser deliberately does not own the room inventory, and the resolver answers "no room called two" against live rooms. Encoding room names in a regex would go stale the day a room is renamed. Suite 162/162 → **181/181**. Mutation: making the ROOM keyword and the hour unit optional (the loose grammar that reintroduces the ambiguity) fails exactly the three disambiguation tests and nothing else. **Also confirmed live this session, unrelated but worth recording:** `schema.json` is stale by 14 additive entries, every one matching a CEO-created field already recorded in F19/F21/F24/F26/F17 — no drift that is not accounted for; and the four `WS_Properties` `Allow Anonymous *` / `Anonymous Override Active` / `Max Anonymous Hourly Duration` fields are **dead schema**, zero code references, and must not be mistaken for an access-control hook.

- F31 — B1: webhook signature verification (X-Hub-Signature-256), plus BUG-10 and the fixture-61 collision. **B1 had never been built.** `CLAUDE.md` rule 25 has asserted "verify HMAC X-Hub-Signature-256 on RAW body" since the contract was written, and the original 5 Jul spec marked it a GATE; a grep of both entry points on `origin/main` returned zero matches for `hmac|x-hub-signature|createHmac|APP_SECRET`. Anyone who learned the webhook URL could POST a forged payload and drive the full state machine — create bookings, hold rooms, trigger cleaner dispatch. The reason it stayed open is a numbering artefact, not a decision: B1 belongs to the **5 Jul** numbering scheme (`WABISTAY_SESSION_BRIEF.md`), which was superseded on **16 Jul** by `Wabistay_Full_Build_Spec_Sequence.md` — a scheme that *starts at B7*. Five of B1–B6 were renumbered into it and shipped under new numbers; B1 alone had no successor slot and was silently dropped, the same failure mode as the "Backlog #2/#8 orphaned" pattern. **Verification is over the RAW bytes and the code refuses to fake it:** Meta signs exactly what it sent, and `JSON.stringify(req.body)` re-serialises to different bytes (key order, whitespace, unicode escaping), so `readRawBody` returns `raw: null` rather than reconstructing — a re-serialised digest would report `verified` while proving nothing, which is worse than no check. This forced `module.exports.config = { api: { bodyParser: false } }` on `api/webhook.js` and a stream read, with the parsed payload re-attached as `req.body` so all six downstream dispatch sites are untouched. **Three modes, and the default is deliberately not a bare 403** — the original spec said "log-only first, then enforce," and that sequencing is load-bearing: two preconditions (the secret being set, and Vercel actually honouring the CJS `bodyParser: false` export) are **unverifiable from a laptop**, and if the second is wrong a bare 403 rejects every webhook the moment the secret lands — Meta retries, then disables the subscription, and Wabistay goes dark. So `HMAC_MODE` unset/`log` verifies and reports but ALWAYS passes through; `enforce` returns 403 before any handler logic; `off` skips entirely. A missing secret is never a pass (fails closed in enforce, loud in log), an unrecognised mode falls back to `log` not `off`, and `no_raw_body` — the exact signal that the parser config didn't take — is reported rather than guessed past. **The gate is NOT closed by this commit; it closes when Shawn sets `HMAC_MODE=enforce` after Axiom confirms `hmac_signature_check` shows `reason: 'verified'` on live traffic.** Rollout order is in `docs/env.md` (NOT `.env.example` — `.gitignore` matches `.env*`, so that file has never been tracked and anything documented solely there is invisible to a fresh clone). `test/hmac.test.js`: 14 tests over digest correctness (genuine/tampered/wrong-secret/malformed/missing header), the re-serialisation trap, all three modes, and router-level proof that forged traffic in enforce mode produces zero sends and zero Airtable writes — a lib-only test would pass while production forwarded forgeries. - F27 — B10.5 BUG 1: `airtableGet` pagination.
