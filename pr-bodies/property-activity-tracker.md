# Property activity tracker (foundation)

**Branch:** `feat/wabistay-property-activity-tracker` → base `feat/wabistay-alert-shawn`

## What this adds
Two new WS_Properties timestamp fields, both best-effort (a write failure here never blocks the guest/owner-facing flow it's attached to):

- **`Last Message Received`** — bumped in `handleMessage`, right after `resolveProperty` succeeds, on every inbound webhook message. `api/wabistay/webhook.js` (see `bumpPropertyActivity`).
- **`Last Owner App Open`** — bumped from the existing WhatsApp delivery-status webhook (`statuses[].status === 'read'`), when the `recipient_id` matches a property's `Notify Phone`.

`Last Report Sent` is **deliberately not a new field**. See "Investigation findings" below.

## Schema dependency (CEO)
Two new fields needed on `WS_Properties` before this can run against production data:
- `Last Message Received` — dateTime
- `Last Owner App Open` — dateTime

Same pattern as the rate-fix-occupancy PR: build is against these exact names; not yet in `schema.json` until Shawn creates them and re-runs `scripts/schema-diff.js --write`. Code reads/writes them at runtime off live records, not off `schema.json`.

I did not create these in the live Airtable base myself — no confirmed write access, and creating production schema isn't something to do silently.

## Investigation findings (as requested)

**"Last Owner App Open" via `account_offboarded`/`account_reconnected`: not usable, and not what those events mean.** Grepped the whole webhook handler (`api/wabistay/webhook.js`) for any Meta event handling beyond `messages` and `statuses` — there is none. More importantly: Meta's WhatsApp Cloud API has **no webhook event for "the user opened their WhatsApp app."** `account_offboarded`/`account_reconnected` are Coexistence-specific events about the *WABA's connection state* (e.g. the Business App disconnecting/reconnecting to the phone number), not a signal about an individual recipient opening their personal app. They wouldn't answer "did this owner check WhatsApp today" even if wired up.

**Proxy used instead: `read` delivery-status receipts.** The webhook already receives and logs delivery-status callbacks (`sent`/`delivered`/`read`/`failed`) at `api/wabistay/webhook.js` (the `statuses` branch, existing B3 code) — it just didn't act on them. A `read` status can only be generated by the recipient's device after they open the conversation, so it's a legitimate (if partial) proxy. Caveat, flagged rather than hidden: this only advances when Meta has something to deliver a status callback on — i.e. when Wabistay actually sent that owner a message recently. An owner who opens WhatsApp but has nothing new from Wabistay to read produces no signal. It undercounts app opens; it does not overcount them (false positives are essentially impossible — you can't mark something read without opening the app).

**"Last Report Sent" is not a new WS_Properties write.** The original ask allowed surfacing it "from existing cron logs" rather than requiring a new field, and for good reason: `runOwnerSummary`/`runDailySummary` have an existing, tested invariant (`test/dailysummary.test.js`, "Rule 29") that both crons are **read-only reporting with zero Airtable writes**. My first pass added a write here and broke that invariant/test (caught by the suite, not shipped). Correct fix: `sendOwnerSummary`/`sendDailySummary` already emit `owner_summary_payload`/`daily_summary_payload` to Axiom on every run, with `propertyId` and the event's own timestamp — that's the existing cron log the task pointed at. "Last Report Sent" for a property is `MAX(_time)` over those two event types filtered by `propertyId`, queryable directly from Axiom with no schema change.

## Judgment call
Two fields on `WS_Properties`, not a new linked table. These are scalar "latest timestamp" values, one per property, same shape as the existing `Notify Phone`/`Daily Summary Hour` fields already there — a linked table would only earn its keep if the tracker needed history (every message, not just the latest), which nothing in this batch asks for.
